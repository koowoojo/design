# UX-KIT

> https://github.com/koowoojo/design/tree/main/ux-kit

요구사항 문서를 입력받아 **UX 구조를 먼저 설계하고 → 화면 시안을 대안으로 제시하고 →
코딩 에이전트가 쓸 수 있는 화면 스펙으로 확정**하는 규칙 모음.

프로젝트마다 나온 교훈을 이 레포에 누적해 규칙을 계속 고도화한다.

---

## 빠른 시작

### 새 프로젝트에 설치

`dist/SETUP-UX-KIT.md` 를 커서 채팅에 첨부하고 **"적용시켜줘"** 라고 입력한다. 끝.

에이전트가 진입점 규칙, 본체 규칙, 조직 컨텍스트, 누적용 폴더를 자동으로 만든다.

파일이 손에 없으면 커서 채팅에 아래를 붙여넣어도 된다.

```
https://raw.githubusercontent.com/koowoojo/design/main/ux-kit/dist/SETUP-UX-KIT.md
이 파일을 받아서 지시대로 설치해줘.
```

레포가 private이면 이 방식은 동작하지 않는다. 파일을 직접 첨부하라.

설치 후 할 일은 없다. 타깃 환경은 세션마다 물어보고, 답한 내용이 `ux-kit/context.md` 에 쌓인다.

### 사용

화면·UI 설계를 요청하면 **자동으로 발동한다.** `@` 호출이 필요 없다.
요구사항 문서(PRD·빌드 프롬프트)를 함께 첨부하면 그것을 입력으로 삼는다.

세션이 끝나면 리포트가 `ux-kit/projects/` 에 자동 저장되고,
**이 레포에 이슈로 올라온다.** 프로젝트 레포에서 파일을 복사해 올 필요가 없다.

## 2단 구조 (진입점 + 본체)

```
src/entry.mdc            ← 진입점 원본. 24줄. 상시 로드되므로 짧게 유지한다
src/UX-UI-RULES.md       ← 본체 원본. 규칙을 고칠 때는 대부분 여기다
context/_template.md     ← 조직 컨텍스트 원본
dist/SETUP-UX-KIT.md     ← 생성물. 직접 수정 금지
```

설치하면 진입점은 `.cursor/rules/ux-kit-entry.mdc` 로, 본체는 `ux-kit/UX-UI-RULES.md` 로 간다.

**왜 나눴나**: 커서의 always-apply 규칙은 모든 세션에 로드된다.
본체(160줄)를 상시 로드하면 백엔드 작업이나 버그 수정을 할 때도 계속 붙어 컨텍스트를 먹는다.
진입점만 상시 두고, 화면 작업이 감지될 때 본체를 읽어오면 체감은 같고 비용만 낮아진다.

**진입점을 늘리지 마라.** 40줄을 넘으면 빌드가 경고한다. 내용은 본체에 넣는다.

규칙을 고쳤으면 반드시 `./build.sh` 를 돌려 배포본을 다시 만든다.
`dist/` 를 손으로 고치면 다음 빌드에서 사라지고, 그 사이에 두 파일이 어긋난다.

```bash
./build.sh
```

빌드는 펜스 개수와 frontmatter 유무를 검증한다. 실패하면 원본이 깨진 것이다.

## 누적 루프

이 레포의 존재 이유다. 프로젝트를 하나 끝낼 때마다 아래를 돈다.

```
프로젝트 레포                          이 레포 (koowoojo/design)
─────────────                          ────────────────────────
1. 세션 종료
   🤖 리포트 생성
   🤖 projects/ 에 저장
   🤖 retro.md 초안 작성
   🤖 learnings/ 대조 · 횟수 +1
                        ── gh issue ──▶  2. 🤖 이슈 자동 등록
                                            [session-report] 매 세션
                                            [promotion]      2회 도달 시

                                         3. 👤 promotion 이슈 검토
                                            ├─ src/UX-UI-RULES.md 수정
                                            ├─ ./build.sh
                                            ├─ CHANGELOG.md 기록
                                            └─ 이슈 close

                                         4. 👤 커밋 · push
                                            → 다음 프로젝트는 갱신본으로
```

🤖 = 자동 / 👤 = 사람이 할 일.

**이슈가 쌓이는 것 자체가 알림이다.** 파일로만 쌓으면 보러 가야 하지만, 이슈는 GitHub이 알려준다.
`promotion` 레이블이 붙은 이슈만 보면 된다. `session-report` 는 근거 보관용이라 평소엔 안 봐도 된다.

**이슈에는 대외비가 들어가지 않는다.** 규칙이 숫자와 이탈 패턴만 담고, 화면 내용·실제 수치·
고객사명은 제외하도록 지시돼 있다. 업스트림에 직접 push하지도 않는다 — 이슈만 만들고,
규칙 수정은 사람이 판단한다.

`gh` CLI를 쓸 수 없는 환경이면 이슈 본문을 화면에 출력한다. 그때만 수동으로 붙여넣으면 된다.

### 왜 2회인가

1회는 우연이고 2회부터 패턴이다. 모든 교훈을 즉시 규칙에 넣으면 규칙이 비대해지고,
컨텍스트만 잡아먹으면서 정작 중요한 지시가 묻힌다.

`learnings/` 는 **승격 대기열**이다. 1회짜리는 여기서 기다린다.
2회째 같은 일이 벌어지면 그때 규칙으로 올린다.

| 경로 | 내용 |
|---|---|
| `src/entry.mdc` | 진입점 원본 (상시 로드, 짧게 유지) |
| `src/UX-UI-RULES.md` | **본체 원본.** 규칙 수정은 대부분 여기 |
| `src/install-header.md` | 설치 지시문. 빌드 시 앞에 붙는다 |

| `context/*.md` | 조직·팀별 인스턴스 (예: `lge-krsales.md`) |
| `projects/` | 프로젝트별 세션 리포트와 회고 |
| `learnings/` | 승격 대기열 |
| `CHANGELOG.md` | 규칙 버전 이력 |

## 규칙을 고쳐야 할 때

아래 신호가 보이면 고친다.

- 같은 것을 에이전트에게 **두 번 이상 설명**하고 있다
- 세션 리포트의 **스펙 이탈이 3회 이상** 나왔다 → 구조 잠금(§7-3) 재설계
- 세션 리포트의 **사용자발 구조 변경이 2회 이상** 나왔다 → UX 단계 체크 항목 부족
- `learnings/` 의 같은 항목에 **발생 횟수가 2가 됐다**

고칠 때 지켜야 할 것:

1. `src/UX-UI-RULES.md` 를 고친다 (진입점 `src/entry.mdc` 는 발동 조건이 바뀔 때만)
2. **추가만 하지 말고 뺄 것을 찾아라.** 규칙이 길어질수록 지켜지지 않는다
3. `./build.sh`
4. `CHANGELOG.md` 에 **무엇을 왜 바꿨고, 어느 프로젝트에서 나온 근거인지** 적는다

## 핵심 가정 (아직 검증 중)

**가정 1 (주)** — 확정된 구조를 에이전트가 이탈하지 않으면 전면 재작업이 발생하지 않는다.

회고에서 드러난 실제 실패 경로:
`확정 → 에이전트가 조용히 구조 변경 → 사용자가 추적 못 함 → "퀄리티가 이게 맞아?" → 전면 재구축`

재작업의 원인은 사용자의 변심이 아니라 **에이전트의 무단 이탈**이었다.
세션 리포트의 **① 스펙 이탈 횟수**가 이 가정의 실측값이다.

**가정 2 (보조)** — UX 선행이 사용자발 구조 변경을 줄인다.
회고 표본 1건뿐이라 **미검증**. 반증되지도 않았다.
화면 수가 많은 프로젝트 1~2건이 누적되면 다시 판정한다.

### 목표 기준선

| 항목 | 현재 | 목표 |
|---|---|---|
| 화면 1개당 소요 | 이틀 이상 | 반나절 |
| 스펙 이탈 (주 지표) | 측정 전 | 0회 |
| 사용자발 구조 변경 | 5회 이상 | 1회 이하 |
| 회귀 | 발생함 | 0회 |

### 실패 기준

**스펙 이탈 3회 이상이 반복되면** 구조 잠금 설계를 갈아엎는다.
개선을 시도하되, 세 프로젝트 연속 이탈 3회 이상이면 이 접근 자체를 접는다.
