# CHANGELOG

규칙(`.cursor/rules/ux-ui-design.mdc`)의 변경 이력.

**기록 규칙**: 무엇을 바꿨는지만 쓰지 마라. **왜 바꿨는지, 어느 프로젝트의 어떤 사건이 근거인지**를 함께 쓴다.
근거가 없는 변경은 다음 사람이(또는 3개월 뒤의 내가) 되돌릴 수 없다.

형식:

```
## [버전] YYYY-MM-DD
### 추가 / 변경 / 제거
- [무엇] — 근거: [프로젝트명] / [무슨 일이 있었는지]
```

## [0.5.0] 2026-09-01

### 추가
- **피드백 업스트림 전달** — 세션 종료 시 `gh issue create` 로 `koowoojo/design` 에
  리포트를 이슈로 등록. 레이블 `session-report`, 승격 대상은 `promotion`.
  근거: 설계 구멍. 리포트가 프로젝트 레포에만 쌓이고 업스트림과 연결이 없어서,
  사람이 파일을 복사해 오지 않으면 누적이 멈추는 구조였다.
  이슈로 보내면 GitHub이 알림을 대신해 주고, 프로젝트 레포와 섞이지도 않는다.

- **`gh` 폴백** — CLI가 없거나 인증 실패 시 이슈 본문을 화면에 출력해 수동 등록 유도.
  조용히 넘어가지 않는다.

- **`context.md` §0 업스트림 레포** — 포크·팀별 분리 대응. `없음` 으로 두면 전송을 끈다.

### 제약
- 이슈 본문에 화면 내용·실제 수치·고객사명 금지. 숫자와 이탈 패턴만 담는다.
- 업스트림에 직접 push 금지. **이슈만 만든다.** 규칙 수정은 사람이 판단한다.

## [0.4.0] 2026-09-01

### 변경
- **`context.md` §1을 「타깃 환경」에서 「환경 레퍼토리」로 재정의.**
  근거: 설계 모순. `context.md` 는 조직 단위로 한 번 만들어 계속 쓰는 파일인데,
  그 안에 프로젝트마다 달라지는 값(이번 프로젝트의 타깃 환경)을 넣으라고 지시하고 있었다.
  조직 컨텍스트에 들어갈 것은 "우리가 반복해서 쓰는 환경들의 목록"이지 "이번 선택"이 아니다.

- **환경은 세션마다 선택한다.** 규칙이 레퍼토리를 번호로 제시하고 사용자가 하나 고른다.
  레퍼토리가 비어 있으면 일반 선택지를 제시한다.

### 추가
- **신규 환경 자동 축적** — 「기타」 선택 시 제약을 파악한 뒤 레퍼토리에 추가를 제안.
  쓸수록 선택지가 늘고 조사할 일이 줄어든다.

- **확인 상태 필드** (`실측` / `문서` / `추정`) — 환경 제약이 실제 확인된 것인지 표시.
  `추정` 환경을 고르면 시안 생성 전에 경고한다.
  근거: v0.2.0의 webOS 제약이 추정값이었는데 확정처럼 기록돼 있었다.
  추정이 사실로 굳으면 그걸 근거로 시안이 만들어진다.

## [0.2.0] 2026-09-01

### 추가
- **§구조 잠금 (Spec Lock)** — 확정된 여정·화면목록·정보위계·영역분할을 잠그고,
  변경하려면 사전 고지 후 승인받도록 강제.
  근거: 회고 결과, 재작업의 원인이 사용자의 변심이 아니라 **에이전트의 무단 구조 변경**이었음.
  사용자가 지시한 적 없는 채팅→신문 레이아웃 전환, AppShell 도입이 발생했고,
  사용자는 항목별로 추적하지 못한 채 "퀄리티가 이게 맞아?"라는 총체적 불만에 도달해 전면 재구축으로 이어짐.

- **이탈 자진 신고 절차** — 작업 중 확정 스펙과 어긋난 것을 알아채면 즉시 신고.
  근거: 이탈을 숨기면 사용자가 개별 지적을 못 하고 전면 재작업으로 간다.

- **"퀄리티가 이게 맞아?" 대응 프로토콜** — 개별 수정 대신 확정 스펙 ↔ 결과물 항목별 대조표부터 출력.
  근거: 같은 회고. 총체적 불만은 이탈 누적 신호이므로 대조가 먼저다.

### 변경
- **주 지표 교체**: `구조 변경 횟수` → `스펙 이탈 횟수`.
  사용자발 구조 변경과 회귀는 보조 지표로 강등.
  근거: 회고 표본에서 사용자발 구조 변경은 1회뿐이었음. 원래 지표는 실제 실패를 측정하지 못했다.

- **실패 기준 재정의**: `구조 변경 3회 이상` → `스펙 이탈 3회 이상`.

- **핵심 가정 3층 구조화**: 가정1(구조 잠금, 주) / 가정2(UX 선행, 보조·미검증) / 가정3(텍스트 판별, 부차).
  근거: 원래 킬러 가정이었던 UX 선행은 표본 부족으로 미검증 상태임을 명시.

## [0.1.0] 2026-09-01

### 최초 작성
구조화 인터뷰(8섹션)를 거쳐 도출.

핵심 설계 결정:
- **파이프라인 6단계**: 입력 → 레퍼런스 → UX 설계 → 텍스트 시안 → 고충실도 렌더링 → 확정
- **대안 제시 강제**: UX는 2안, 시안은 3안, 각각 추천안과 근거 명시
- **레퍼런스 선정 기준**: 같은 화면 유형 > 같은 사용 맥락 > 같은 업계.
  "의도적으로 먼 업계"는 3안 중 도전형 자리에 투입
- **시안 대안 축**: 정보 위계 > 상호작용 방식 > 안전–도전 배치.
  디자인 톤은 텍스트 단계의 축이 아님(판별 불가) — 렌더링 단계로 이동
- **UX 출력 순서**: 여정 → 화면목록 → 핵심순간 → 위계는 후보만.
  여정을 먼저 하는 이유는 화면 목록부터 만들면 로그인·설정 같은 관행적 화면이 자동으로 끼어들기 때문
- **렌더링 수단**: HTML/CSS 단일 파일 > SVG > 이미지 생성 프롬프트.
  이미지는 보고 버려지지만 코드는 구현 출발점이 됨
- **타깃 환경을 필수 입력으로 승격**: 최대 리스크(구현 불가능한 시안)를 구조적으로 제거
- **대외비 처리**: 검색 쿼리에 고유명사·수치 금지, 시안 데이터는 전부 더미
- **AI 자율 범위**: 레퍼런스 수집·일관성 검사·룰 파일 생성은 단독 수행. UX와 시안은 대안 제시
