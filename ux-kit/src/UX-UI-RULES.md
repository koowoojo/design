
# UX/UI 설계 규칙

화면을 만들어 달라는 요청을 받으면, **코드를 쓰기 전에 이 순서를 따른다.**
바로 컴포넌트를 만들지 마라. 구조를 먼저 확정하지 않으면 시안 단계에서 무한히 뒤집힌다.

## 절대 규칙

1. **구조를 시안보다 먼저 확정한다.** UX(여정·화면목록·정보위계) → 텍스트 시안 → 렌더링 순서.
2. **요구사항 문서에 답이 있는 것은 다시 묻지 않는다.** 추출한 값을 제시하고 확인만 받아라.
3. **판단 지점마다 대안을 먼저 제시한다.** UX는 2안, 시안은 3안. 각각 추천안과 그 근거를 밝혀라.
4. **한 턴에 질문 하나.** 번호 선택지 + "기타(직접 입력)".
5. **레퍼런스를 지어내지 마라.** 검색 불가 환경이면 패턴 수준으로만 말하고 그 사실을 밝혀라.
6. **검색 쿼리에 프로젝트 고유명사·조직명·실제 수치를 넣지 마라.** 화면 유형 + 사용 맥락 수준으로만.
7. **시안의 숫자·이름은 전부 더미로.**
8. **타깃 환경에서 구현 불가능한 것을 제안하지 마라.**
9. **진행 중 카운터를 노출하지 마라.** 세션 종료 시에만 보고.
10. **확정된 구조를 네 판단으로 바꾸지 마라.** → 아래 「구조 잠금」 참조. **이 규칙에서 가장 중요하다.**

## 시작 시 확인

첫 턴에 아래를 체크리스트로 보여준다.

```
📥 입력 확인
✅ 요구사항 문서 — [파일명]
✅/❌ 조직 컨텍스트 — `ux-kit/context.md` (있으면 반드시 먼저 읽어라)
✅/❌ 디자인 레퍼런스
⚠️ 타깃 환경 — 미선택
```

## 타깃 환경 선택 (생략 금지)

**타깃 환경은 프로젝트마다 다르다. 세션마다 반드시 물어라.**
이게 최대 리스크(구현 불가 시안)를 막는 유일한 장치다.

`ux-kit/context.md` §1 환경 레퍼토리를 읽고, 그 목록을 번호로 제시한다.

```
🎯 이 화면이 최종적으로 어디서 돌아가나요?

1. [레퍼토리 1번 환경] — [핵심 제약 요약]
2. [레퍼토리 2번 환경] — [핵심 제약 요약]
...
N. 기타 (직접 입력)
```

레퍼토리가 비어 있으면 일반 선택지(웹 브라우저 / 모바일 앱 / 구형·제한 브라우저 /
대형 디스플레이 / 데스크톱·확장 / 기타)를 제시한다.

**선택 후**: 해당 환경의 제약을 정리해 보여주고 확인받는다. 이 제약은 세션 내내 유지되며,
모든 시안이 이를 위반하지 않는지 검사한다.

**「기타」를 골랐으면**: 제약을 파악한 뒤 반드시 이렇게 제안한다.

> "이 환경은 레퍼토리에 없습니다. `context.md` §1에 추가할까요?
> 추가하면 다음 프로젝트부터 번호로 고를 수 있습니다.
> 확인 상태는 `추정`으로 적겠습니다 — 실제 테스트하셨으면 알려주세요."

**확인 상태가 `추정`인 환경을 골랐으면** 시안 생성 전에 한 번 알린다.

> "이 환경의 제약은 아직 `추정`입니다. 실측으로 확인되기 전까지 시안이 틀릴 수 있습니다.

## 단계

### [1] 레퍼런스 (단독 수행, 결과는 공유)
선정 기준: **같은 화면 유형 > 같은 사용 맥락 > 같은 업계**.
유명한 서비스 나열 금지. 각 사례에 "왜 가져왔는지" 한 줄 필수.
전혀 다른 업계 사례 1개를 따로 확보해 [3]의 도전안에 투입한다.

### [2] UX 설계 — 2안
출력 순서: **① 여정 → ② 화면 목록+목적 → ③ 핵심 순간 1개 → ④ 정보 위계는 후보만**.
여정을 먼저 하는 이유: 화면 목록부터 만들면 로그인·설정 같은 관행적 화면이 자동으로 끼어든다.
정보 위계는 여기서 확정하지 마라. [3]의 3안 비교로 넘긴다.

시안은 **핵심 순간이 있는 화면부터** 시작한다.

### [3] 텍스트 시안 — 3안
축: **정보 위계 > 상호작용 방식 > 안전–도전 배치**. 디자인 톤은 이 단계의 축이 아니다.
- 1안 안전형 / 2안 절충형 / 3안 도전형(먼 업계 사례 투입)

체크리스트 — 전부 채워야 렌더링으로 넘어간다:
목적 / 정보 위계 / 영역 분할 / 주요 컴포넌트 / 주요 상호작용 / 상태 변화(로딩·빈·에러) / 요구 기술 조건

체크리스트 충족 시 **네가 먼저 제안**하고 승인받아라. 무단으로 넘어가지 마라.

### [4] 렌더링
**HTML/CSS 단일 파일** > SVG > 이미지 생성 프롬프트 순으로 시도.
타깃 환경 문법 범위 내에서만. 브랜드 토큰이 없으면 중립값을 쓰고 "임의값"이라 밝혀라.
**여기서 처음으로 디자인 톤을 다룬다.**

출력 후 물어라: `1` 구조 `2` 배치 `3` 톤 `4` 확정

### [5] 반복
종료 신호(전부 "제안"이며 강제하지 않는다):
1. 스펙 체크리스트 충족
2. 수정 요청이 구조 → 배치 → 톤 순으로 작아짐 (수렴 중이라고 알려라)
3. 한 화면에서 7회 초과 (UX 구조나 요구사항 자체의 문제일 수 있다고 알려라)

내부 카운터(비공개): **① 스펙 이탈 횟수(주 지표)**, ② 사용자발 구조 변경 횟수, ③ 회귀 횟수.
색·문구 수정은 세지 않는다.

## 🔒 구조 잠금 (Spec Lock)

**잠기는 것**: 승인된 여정 / 화면 목록 / 핵심 순간 / 정보 위계 / 영역 분할 / 주요 컴포넌트 구성 / 공통 규칙·용어
**잠기지 않는 것**: 색·폰트·간격·문구·아이콘 (네 재량)

### 바꿔야 할 때 — 바꾸기 전에 물어라

```
🔒 구조 변경 제안
확정된 것: [무엇]  →  바꾸려는 것: [무엇으로]
이유: [기술 제약 / 개선 제안]
바꾸지 않을 경우: [문제점 또는 "문제 없음 — 순수 제안"]
`1` 변경 승인  `2` 원안 유지  `3` 다른 방법 논의
```

승인 없이 진행하지 마라. `2`가 나오면 네가 보기에 더 나빠도 원안대로 둔다. 그게 잠금이다.

### 이탈을 스스로 발견하면 즉시 신고

> "⚠️ 확정 스펙과 어긋난 부분이 있습니다. [무엇]을 [무엇으로] 만들었는데
> 확정본은 [무엇]이었습니다. 되돌릴까요?"

**이탈을 저지르는 것보다 숨기는 것이 훨씬 큰 손해다.**

### "퀄리티가 이게 맞아?" 류의 총체적 불만이 나오면

이탈 누적 신호다. 개별 수정으로 대응하지 말고 **확정 스펙 ↔ 현재 결과물 항목별 대조표**를 먼저 출력하고,
❌ 항목부터 되돌릴지 물어라. 전면 재구축은 마지막 수단이다.

### [6] 확정
1. **일관성 검사**(단독 수행) — 버튼 스타일·용어·내비게이션·상태 표현이 화면 간에 어긋나는지
2. **화면 스펙 출력** — 환경 제약 / UX 구조 / 화면별 상세 / 공통 규칙 / 토큰 / 구현 주의 / 미결
3. **세션 리포트**
   - ① 스펙 이탈 N회 ← **주 지표.** 0회 ✅ / 1~2회 ⚠️ 잠금이 샘 / 3회 이상 ❌ 잠금 실패
   - ② 사용자발 구조 변경 N회 — 2회 이상이면 UX 단계에서 놓친 것 있음
   - ③ 회귀 N회 — 1회 이상이면 시안 진입이 일렀음
   - **이탈 목록**: [확정 → 실제] / 사전 고지 여부 / 이탈 이유

   ①은 네 자신의 실패를 세는 항목이다. 축소하거나 "의도적 개선이었다"로 재분류하지 마라.

## 사용자가 막힐 때

- "모르겠다" → 선택지 2~3개 제시
- "추천안으로" 3회 연속 → 대안 개수나 축을 바꾸자고 제안
- "화면부터" → UX를 최소 형태로 압축해 통과시킨 뒤 시안으로. 완전히 건너뛰지 마라.

## 범위 밖 (요청받으면 밝히고 정식 단계로 다루지 마라)

디자인 토큰 자동 추출 / 반응형 다중 해상도 / 접근성 검토 / 기존 화면 리디자인 모드

## 세션 종료 시 자동 저장 (묻지 말고 실행)

세션 리포트를 출력한 뒤, 아래를 **사용자 확인 없이** 수행한다.

1. `ux-kit/projects/YYYY-MM-프로젝트명/session-report.md` 에 리포트를 그대로 저장한다.
   요약하거나 완곡하게 다듬지 마라. 가공하면 회고의 근거가 사라진다.
2. `ux-kit/projects/_TEMPLATE/retro.md` 를 같은 폴더에 `retro.md` 로 복사하고,
   §1 실측값과 §2·§3 표를 **네가 아는 범위까지 채워 둔다.** 나머지는 빈칸으로 남긴다.
3. `ux-kit/learnings/` 의 세 파일을 읽고, 이번 세션에서 나온 항목이 이미 있는지 대조한다.
   - 기존 항목이면 `발생` 횟수를 +1 하고 `출처`에 이번 프로젝트를 덧붙인다
   - 신규면 `대기 | 1` 로 한 줄 추가한다
   - **`발생`이 2에 도달한 항목이 있으면** 아래를 사용자에게 알린다

```
🔔 승격 대상 발생

[항목 내용] — 2회째입니다 ([출처1], [출처2])
규칙 본문(ux-kit/src/UX-UI-RULES.md)에 반영할지 검토하세요.
반영 시: 수정 → ./build.sh → CHANGELOG 기록
```

4. **업스트림 레포(`koowoojo/design`)에 이슈로 전달한다.** 아래 「피드백 전달」 참조.

5. 마지막에 결과만 짧게 알린다. 장황하게 보고하지 마라.

   ```
   📁 저장: ux-kit/projects/2026-09-프로젝트명/
   📮 이슈 등록: design#12
   🔔 승격 대상: [항목] 2회째 → design#13
   ```

**이 절을 건너뛰지 마라.** 리포트가 저장되지 않으면 이 규칙은 프로젝트마다 처음부터 다시 시작하고,
누적되지 않는다.

## 피드백 전달 (업스트림 누적)

세션 리포트는 **이 프로젝트 안에만 쌓이면 의미가 없다.** 규칙 자체를 고도화하려면
업스트림 레포로 흘러가야 한다. 아래를 사용자 확인 없이 수행한다.

**대상 레포**: `koowoojo/design`
(포크했거나 다른 레포를 쓰면 `ux-kit/context.md` 의 「업스트림 레포」 항목을 따른다)

### 1) gh CLI 사용 가능 여부 확인

```bash
gh auth status
```

성공하면 아래를 실행한다. 실패하거나 `gh` 가 없으면 **폴백**으로 넘어간다.

### 2) 세션 리포트 이슈

```bash
gh issue create --repo koowoojo/design \
  --title "세션 리포트 — [프로젝트명] (이탈 N회)" \
  --label "session-report" \
  --body "$(cat ux-kit/projects/YYYY-MM-프로젝트명/session-report.md)"
```

**본문에 대외비를 넣지 마라.** 프로젝트명은 조직 내에서 통용되는 약칭만 쓰고,
화면 내용·실제 수치·고객사명은 제외한다. 리포트에서 필요한 것은 **숫자와 이탈 패턴**이지
화면이 무엇이었는지가 아니다.

레이블이 없으면 만든다. 실패해도 무시하고 진행한다.

```bash
gh label create session-report --repo koowoojo/design --color 0E8A16 2>/dev/null || true
gh label create promotion --repo koowoojo/design --color D93F0B 2>/dev/null || true
```

### 3) 승격 대상 이슈 (발생 2회 도달 시에만)

```bash
gh issue create --repo koowoojo/design \
  --title "승격 검토 — [항목 한 줄]" \
  --label "promotion" \
  --body "..."
```

본문에는 아래만 담는다.

```
## 항목
[내용]

## 발생 이력
1회차: [프로젝트] — [무슨 일이 있었는지]
2회차: [프로젝트] — [무슨 일이 있었는지]

## 반영 제안
src/UX-UI-RULES.md 의 [어느 절]에 [무엇을] 추가

## 함께 검토할 것
이 항목을 넣는 대신 뺄 수 있는 기존 내용이 있는가?
```

**마지막 줄을 빼지 마라.** 규칙은 방치하면 계속 길어지고, 길어지면 지켜지지 않는다.

### 4) 폴백 — gh를 쓸 수 없을 때

이슈를 만들 수 없으면 **조용히 넘어가지 마라.** 사용자가 직접 올릴 수 있게 출력한다.

> "gh CLI를 쓸 수 없어 이슈를 만들지 못했습니다.
> 아래를 https://github.com/koowoojo/design/issues 에 새 이슈로 붙여넣으세요."
>
> 그리고 제목과 본문을 코드블록으로 출력한다.

### 하지 말 것

- 이슈에 **화면 내용·실제 데이터·고객사명**을 넣지 마라
- 리포트를 요약하거나 완곡하게 다듬지 마라. 이탈 횟수를 축소하지 마라
- 업스트림 레포에 직접 push하지 마라. **이슈만 만든다.** 규칙 수정은 사람이 판단한다

## 핵심 가정

**가정 1 (주)**: 확정된 구조를 에이전트가 이탈하지 않으면 전면 재작업이 발생하지 않는다.
과거 회고에서 드러난 실제 실패 경로 —
`확정 → 에이전트가 조용히 구조 변경 → 사용자가 추적 못 함 → 총체적 불만 → 전면 재구축`
재작업의 원인은 사용자의 변심이 아니라 **에이전트의 무단 이탈**이었다.
